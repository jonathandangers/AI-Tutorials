Module 06

Plan the work, finish a stage, save what you trust, then continue.

For anything bigger than one sitting: a grant section, a curriculum, a database, a lecture series. Each step below says what to do, what to ask, what to save, and how you know you are done.

Pocket card

  • The project home is the record. Chats are temporary.
  • One stage per chat. Approve it, export it, then move on.
  • Repeated instructions become project instructions or a skill.

What a project home contains

Set this up once. Every later step reads from it or writes to it.

ItemWhat goes in itChanges
Project descriptionGoal, audience, requirements, background, constraints, what success looks likeRarely
Current stateOne page: the plan, what is done, decisions made, what is nextAfter every stage
Approved outputsFinished pieces you have checked and would stand behindAs stages finish
Reference filesPapers, templates, data, links, and other documents the work relies onAs you go

  1. Create the project home.

    Choose the desktop or cloud location where the durable project memory and approved outputs will live. Create the four items above, even if they are empty.

    Then create a platform project (a Claude or ChatGPT project) for the same work. Its instructions say what the project is and where the current state lives. The model still needs the files themselves: upload them to each chat, or connect the tool to the folder and confirm it can read them.

    Done when: both exist and the project instructions point to the home.

  2. Describe the project.

    Brain-dump the goal, background, constraints, source material, and what a successful final result should look like. Talk or type; do not polish it.

    Ask
    Turn this brain-dump into a one-page project description: goal, audience, requirements, background, constraints, and what success looks like. Then list what is missing or unclear before you could plan the work.

    Answer its questions, fix what it got wrong, and save the project description to the home. Paste the short version into the project instructions.

    Done when: someone else could read the project description and understand what you are making and why.

  3. Build and refine a plan.

    Ask the LLM to organize the project into stages. Each stage needs an output and a test for when it is finished.

    Ask
    Using the project description, propose 3–6 stages. For each: the output it produces, what it depends on, and how I will know it is done. Flag the stage most likely to go wrong.

    Push back until it fits: too many stages, wrong order, a stage that is really two. Save the plan in the current-state document.

    Done when: the plan accurately reflects what you are trying to do and the order you would actually do it.

  4. Work one stage at a time.

    Open a new chat for the stage inside the platform project. Give it the project description, the current state, and any approved outputs or reference files that stage depends on. Iterate, critique, and verify, using Module 04.

    When the stage is solid, export it: save the output to Approved outputs and update the current-state document with what was done, what was decided, and what comes next.

    Ask
    Update the current-state document: mark this stage done, list the decisions we made and why, and state the next stage and what it needs from this one.

    Done when: you would stand behind the output, and the current-state document is accurate without the chat.

  5. Continue from the trusted state.

    Move to the next stage in a fresh chat. Because the project instructions and the home carry the state, the new chat starts already oriented. You do not need the old conversation.

    If you notice yourself typing the same instructions at the start of each chat, move them into the project instructions or turn them into a skill.

    Done when: every planned stage has an approved output.

  6. Review the final product as a whole.

    Check that the pieces fit together and that you understand and stand behind the finished result. Read it end to end, then ask a model to review it as the intended audience would.

    Ask
    Read this as [the intended audience]. What is unclear, inconsistent between sections, or unsupported? What would you ask the author?

    Done when: you can explain every part without the model, and the important facts have been checked against their sources.

When something changes

Projects get revised after they are done: a reviewer's comments, a new deadline, a better idea. You do not need a new process. A revision is one more pass through the same loop.

Revise one piece. Open a new chat. Give it the project description, the current state, and the approved output you are changing. When the new version is solid, replace the old one in Approved outputs, then note what changed and why in the current state.

If the goal changes, start with the project description. Update it before any other work, then check the plan against it. Every new chat reads the description first, so a stale one points each of them in the wrong direction.

Keep one approved version. Replace the old output rather than keeping "final" and "final v2" side by side. If you want the history, move the old version to an archive folder.

Ask
The project description changed: [what changed]. Using the current state, list which approved outputs are affected and which stages need to be redone, in order.

Done when: the project description, the current state, and the approved outputs agree with each other.
