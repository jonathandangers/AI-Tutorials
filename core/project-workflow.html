Module 06

Running larger projects

06

Pocket card

  • New topic, new chat. When a chat grows long, save what you trust and start fresh.
  • Keep a project home outside the chat: a folder with the description, the current state, approved outputs, and reference files.
  • Work one stage per chat. Approve it, export it, then move on.
  • Instructions you keep retyping belong in project instructions or a skill.

This module is for work that takes more than one sitting: a lecture series, a teaching website, a curriculum, a database. The first half explains how chats and memory behave. The second half is a six-step workflow built on that.

A single chat is often enough. An email, a summary, a quick question, or a first brainstorm can start and finish in one chat. Set up a project home once the work will span several sessions, or once losing the chat would cost you something.

How chats and memory behave

A chat, sometimes called a thread or a conversation, is one continuous exchange with the model. The model works from what is in the current chat. As the chat grows, there is more for it to process. That consumes more of your plan's usage, and in a very long chat the model can lose track of which instruction is the current one.

Start a new chat when you change topics. For long-running work, start fresh when the existing chat has become unwieldy. Before you leave, export what you approved to the project home: the finished output and an updated current-state document. The next chat starts from those, so nothing depends on the old one.

Four layers of memory

Platform memory and platform projects are helpful, and they live inside one vendor's product. The project home is a folder you control. It survives a long chat, gives you a clean place to restart, lets you hand the work to another model or person, and keeps trusted outputs separate from the exploratory conversation that produced them.

The platform project and the project home work together. The project's instructions tell the model what the work is and where the current state lives. The home holds what you have approved. Naming the folder in the instructions gives the model no access to it, so upload the current-state document and the files a task needs at the start of each chat, or connect the tool to the folder and confirm it can read the files.

The loop

The example below is a teaching site on eye emergencies, built from existing lecture notes. All of it is public teaching material, so a personal AI account is appropriate.

What a project home contains

Set this up once. Every later step reads from it or writes to it.

ItemWhat goes in itChanges
Project descriptionGoal, audience, requirements, background, constraints, what success looks likeRarely
Current stateOne page: the plan, what is done, decisions made, what is nextAfter every stage
Approved outputsFinished pieces you have checked and would stand behindAs stages finish
Reference filesLecture notes, papers, guidelines, templates, and other documents the work relies onAs you go

The six steps

  1. Create the project home.

    Choose the desktop or cloud location where the durable project memory and approved outputs will live. Create the four items above, even if they are empty.

    Then create a platform project (a Claude or ChatGPT project) for the same work. Its instructions say what the project is and where the current state lives. The model still needs the files themselves: upload them to each chat, or connect the tool to the folder and confirm it can read them.

    Done when: both exist and the project instructions point to the home.

  2. Describe the project.

    Brain-dump the goal, background, constraints, source material, and what a successful final result should look like. Talk or type, and leave it unpolished.

    Ask
    Turn this brain-dump into a one-page project description: goal, audience, requirements, background, constraints, and what success looks like. Then list what is missing or unclear before you could plan the work.

    Answer its questions, fix what it got wrong, and save the project description to the home. Paste the short version into the project instructions.

    Done when: someone else could read the project description and understand what you are making and why.

  3. Build and refine a plan.

    Break the project into stages yourself, or at least choose them. You know the work and where it is likely to go wrong. The model can then organize your stages and check them for gaps. Each stage needs an output and a test for when it is finished.

    Ask
    Here are the stages I have in mind: [your list]. Using the project description, organize them. For each: the output it produces, what it depends on, and how I will know it is done. Tell me if a stage is missing or is really two, and flag the one most likely to go wrong.

    If you cannot see the stages yet, ask the model to propose 3–6 and choose from those. Adjust until the plan fits: too many stages, wrong order, a stage that is really two. Save the plan in the current-state document.

    Done when: the plan accurately reflects what you are trying to do and the order you would actually do it.

  4. Work one stage at a time.

    Open a new chat for the stage inside the platform project. Give it the project description, the current state, and any approved outputs or reference files that stage depends on. Iterate, critique, and verify, as described in Iterate and verify.

    When the stage is solid, export it: save the output to Approved outputs and update the current-state document with what was done, what was decided, and what comes next.

    Ask
    Update the current-state document: mark this stage done, list the decisions we made and why, and state the next stage and what it needs from this one.

    Done when: you would stand behind the output, and the current-state document is accurate without the chat.

  5. Continue from the trusted state.

    Move to the next stage in a fresh chat. The project instructions and the home carry the state, so the new chat starts already oriented and the old conversation can be left behind.

    If you notice yourself typing the same instructions at the start of each chat, move them into the project instructions or turn them into a skill.

    Done when: every planned stage has an approved output.

  6. Review the final product as a whole.

    Check that the pieces fit together and that you understand and stand behind the finished result. Read it end to end, then ask a model to review it as the intended audience would.

    Ask
    Read this as [the intended audience]. What is unclear, inconsistent between sections, or unsupported? What would you ask the author?

    Done when: you can explain every part without the model, and the important facts have been checked against their sources.

The whole workflow at a glance

Steps 1 to 3 happen once. Steps 4 and 5 are the loop shown above, repeated for each stage. Step 6 happens once at the end.

  2. Describe the projectSaves the project description
  3. Build a planSaves the plan in the current state

Repeat for each stage

  1. Work one stage in a new chatSaves the approved output and updates the current state
  2. Continue from the homeThe next stage starts in a fresh chat

Back to step 4 until every stage has an approved output.

Finish

  1. Review the whole productRead it end to end and check that the pieces fit

When something changes

Projects get revised after they are done: a reviewer's comments, a new deadline, a better idea. A revision is one more pass through the same loop.

Revise one piece. Open a new chat. Give it the project description, the current state, and the approved output you are changing. When the new version is solid, replace the old one in Approved outputs, then note what changed and why in the current state.

If the goal changes, start with the project description. Update it before any other work, then check the plan against it. Every new chat reads the description first, so a stale one points each of them in the wrong direction.

Keep one approved version. Replace the old output, so there is never a "final" and a "final v2" side by side. If you want the history, move the old version to an archive folder.

Ask
The project description changed: [what changed]. Using the current state, list which approved outputs are affected and which stages need to be redone, in order.

Done when: the project description, the current state, and the approved outputs agree with each other.
